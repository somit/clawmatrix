# A2A Async Delegation

This document defines the implementation direction for agent delegation in ClawMatrix.

The short version: use A2A as the default Clutch-Control Plane protocol for delegation and task tracking. ClawMatrix owns the A2A boundary; target runtimes such as OpenClaw, PicoClaw, Claude Code, and custom runners do not need native A2A support.

## Goal

`clutch delegate` currently uses ClawMatrix-specific HTTP endpoints and blocks until the target agent responds. Long-running work such as log analysis, health checks, and incident investigation can take many minutes, tying up the caller and exposing timeout mismatches between ClawMatrix and the target runtime.

Async delegation should let the caller submit work, receive a durable handle immediately, and inspect status or output later.

Because ClawMatrix is not public-stable yet, we do not need to preserve the old delegation protocol. Replace Clutch-Control Plane delegation with A2A instead of adding a parallel compatibility layer.

## Core Model

Use A2A's core objects:

- `Task.id`: the specific async run/task, generated by the server.
- `Task.contextId`: the contextual collection of related interactions, generated by the server.
- `Task.status`: a `TaskStatus` object containing `state`, optional `message`, and optional `timestamp`.
- `Task.history`: A2A `Message` objects exchanged during the task.
- `Task.artifacts`: A2A `Artifact` objects generated by the target agent.
- `Task.metadata`: ClawMatrix-specific routing and runtime details.

One `contextId` can contain multiple tasks. For example, "investigate health", "continue with yesterday's comparison", and "prepare handoff summary" should share context but have separate task state.

ClawMatrix should publish A2A Agent Cards from the agent information it already has:

- `agentDiscovery` from clutch runners.
- `AgentProfile` name, description, registration, and deployment config.
- `Agent.Meta` fields such as `chatUrl`, `workspaceUrl`, `sessionsUrl`, and `runner`.
- Connection graph entries that define which agent profiles can call each other.

The card is profile-level first: `/a2a/ratchet` represents the `ratchet` profile and ClawMatrix routes to one healthy concrete `ratchet` instance. Instance-level cards can come later if needed.

## Default Protocol

Clutch talks to ClawMatrix over A2A for delegation:

```text
clutch delegate
  -> A2A JSON-RPC message/send
  -> ClawMatrix /a2a/{target-profile}
  -> selected target clutch /ask/{local-agent}
  -> runner backend
```

ClawMatrix still uses existing runner execution behind the A2A boundary. A2A does not require OpenClaw or other runners to implement A2A natively.

A2A-native callers do not need Clutch as a client shim. They can discover an Agent Card and call ClawMatrix `/a2a/{target-profile}` directly.

Whether they should bypass Clutch depends on the caller's security and runtime needs. Clutch is still the security/runtime gateway when the caller needs:

- the local runner host for OpenClaw, PicoClaw, Claude Code, and custom executors
- the CLI for humans and non-A2A agent runtimes
- the local gateway for workspace, session, and egress-control integration
- sniffer mode, network monitoring, and allowlist enforcement near the runtime
- per-runtime process isolation and token handling

So there are two valid caller modes:

- direct A2A caller -> ClawMatrix, for runtimes that already handle their own execution and security boundary
- caller -> local Clutch -> ClawMatrix, for runtimes that want ClawMatrix security controls enforced through Clutch

## CLI UX

Synchronous delegation:

```bash
clutch delegate ratchet "check current API error rate"
```

Async delegation:

```bash
clutch delegate --async ratchet \
  "full health check and error rate analysis" \
  "health-2026-03-17"
```

Response:

```json
{
  "kind": "task",
  "id": "task_01HR...",
  "contextId": "ctx_01HR...",
  "status": {
    "state": "submitted",
    "timestamp": "2026-06-01T09:45:00Z"
  },
  "metadata": {
    "clawmatrix": {
      "target": "ratchet",
      "source": "optimus",
      "session": "delegate:optimus:health-2026-03-17",
      "statusUrl": "/tasks/task_01HR...",
      "sessionUrl": "/agents/ratchet/sessions?name=delegate-optimus-health-2026-03-17.jsonl"
    }
  }
}
```

Readback:

```bash
clutch tasks get task_01HR...
clutch session ratchet "delegate-optimus-health-2026-03-17.jsonl"
```

## Lifecycle

Initial state machine:

```text
submitted -> working -> completed
submitted -> working -> failed
submitted -> working -> input-required
submitted -> rejected
submitted -> canceled
submitted -> auth-required
```

Use A2A `TaskState` values:

- `submitted`: control plane accepted the delegation.
- `working`: target chat request has started.
- `input-required`: target needs caller/user input to continue.
- `completed`: target returned successfully.
- `canceled`: caller canceled before completion.
- `failed`: target returned an error, became unreachable, or exceeded its max runtime.
- `rejected`: target rejected the task before starting.
- `auth-required`: target needs authentication to proceed.
- `unknown`: fallback for indeterminate state.

## Data Model

Add a control-plane `tasks` table that stores A2A `Task` fields directly:

```text
id                  string primary key
kind                string default "task"
context_id          string index
runtime_session     string
runtime_runner      string
status_state        string index
status_message      json
status_timestamp    time
history             json
artifacts           json
metadata            json
source_agent_id     string
source_profile      string
target_agent_id     string
target_profile      string
created_at          time
updated_at          time
```

The API should serialize rows as A2A `Task` objects. Source/target columns are indexes for ClawMatrix authorization and filtering; the portable protocol data lives in `status`, `history`, `artifacts`, and `metadata`.

`context_id` is A2A protocol identity. `runtime_session` is the runner-specific session name. Keep them separate because OpenClaw, PicoClaw, Claude Code, and custom runners encode session names differently. For OpenClaw, `delegate:optimus:health-2026-03-17` may become `delegate-optimus-health-2026-03-17.jsonl` on disk.

`sessionUrl` is provider-specific and should be generated by the runner or by a runner-aware helper. Do not assume `runtime_session + ".jsonl"` is enough. Some providers normalize separators, add prefixes, nest sessions under encoded workspace paths, or use provider-native session IDs unrelated to the public A2A `contextId`.

On control-plane startup, any task still in `submitted` or `working` from a previous process should be marked `unknown` with a status message explaining that the process restarted before completion tracking finished. A durable queue can replace this later.

## Agent Card

Agent Card discovery is Phase 1, not a later add-on.

ClawMatrix should generate cards from the existing registration/discovery model:

```http
GET /.well-known/agent-card.json?agent=ratchet
GET /a2a/ratchet/agent-card.json
```

Example shape:

```json
{
  "name": "ratchet",
  "description": "Ratchet agent profile",
  "url": "https://cp.example.com/a2a/ratchet",
  "version": "0.1.0",
  "capabilities": {
    "streaming": false,
    "pushNotifications": false,
    "stateTransitionHistory": true
  },
  "defaultInputModes": ["text/plain"],
  "defaultOutputModes": ["text/plain"],
  "securitySchemes": {
    "bearer": {
      "type": "http",
      "scheme": "bearer",
      "bearerFormat": "JWT"
    }
  },
  "security": [{ "bearer": [] }],
  "skills": [
    {
      "id": "delegate",
      "name": "Delegate work to ratchet",
      "description": "Submit operational or engineering tasks to the ratchet agent."
    }
  ]
}
```

`skills` can start generic and become richer when agents publish explicit capability metadata.

## Auth And Visibility

A2A auth is HTTP-level. The JSON-RPC payload should not carry credentials.

Support bearer auth first:

```http
Authorization: Bearer <token>
```

Token handling:

- Human JWT: enforce existing RBAC and profile ACLs.
- Agent token: enforce the connection graph. A source agent can call only connected target profiles.
- Future service token or OIDC client: enforce explicit scopes/profile permissions.

Task visibility:

- The source agent can read its own submitted tasks.
- The target agent can read tasks assigned to it.
- Humans need the relevant profile permission, or admin-level permission.
- `tasks/get`, `tasks/cancel`, session readback, and convenience REST endpoints must all use the same visibility checks.

Authorization failures should return A2A/JSON-RPC errors, not ad hoc response bodies.

## API Sketch

Primary A2A-compatible JSON-RPC endpoint:

```http
POST /a2a/{agent}
Content-Type: application/json
```

Start or continue work with `message/send`:

```json
{
  "jsonrpc": "2.0",
  "id": "req-001",
  "method": "message/send",
  "params": {
    "message": {
      "kind": "message",
      "messageId": "msg_01HR...",
      "role": "user",
      "parts": [
        { "kind": "text", "text": "full health check" }
      ],
      "contextId": "ctx_01HR..."
    }
  }
}
```

Response result is an A2A `Task` or `Message`. For long-running work, return a `Task` in `submitted` or `working` state.

Task inspection and cancellation use A2A method names:

```json
{ "jsonrpc": "2.0", "id": "req-002", "method": "tasks/get", "params": { "id": "task_01HR..." } }
{ "jsonrpc": "2.0", "id": "req-003", "method": "tasks/cancel", "params": { "id": "task_01HR..." } }
```

Convenience REST endpoints can exist for ClawMatrix UI:

```http
GET /tasks/{id}
GET /tasks?contextId=...&status=...
POST /tasks/{id}/cancel
GET /agent-sessions/{agent}?name={session}.jsonl
```

The session endpoint can proxy to the target clutch gateway's existing `/sessions?name=...` endpoint.

JSON-RPC error handling should be explicit:

- unknown method -> method not found
- malformed params -> invalid params
- auth failure -> authorization error
- no connected target -> authorization error
- no healthy target instance -> target unavailable
- unsupported streaming/cancel/push feature -> unsupported operation

Use HTTP status only for transport-level failures. Protocol failures should be JSON-RPC errors.

## Artifacts And History

For the first useful version, emit two artifacts on completion:

- final text response from the target agent
- target runtime session link

Do not copy the full runtime JSONL session into the task row. Keep compact A2A `history` for protocol-level messages and link to the runtime session for detailed readback.

If a task fails after partial work, preserve the runtime session link as an artifact when available.

## Local Delegation

Current clutch can short-circuit same-instance delegation directly to a local agent. For A2A async tasks, control-plane tracking still needs to happen.

Rule:

- synchronous local delegation may keep the current fast path
- async/A2A delegation must create a control-plane `Task` first

That guarantees `tasks/get`, auth, audit, and artifacts behave consistently regardless of whether source and target live in the same clutch process.

## Phases

Phase 1:

- Add `Task` model using A2A field names.
- Add Agent Card generation from `AgentProfile`, `Agent.Meta`, and runner discovery metadata.
- Add `POST /a2a/{agent}` with `message/send`, `tasks/get`, and JSON-RPC errors.
- Move Clutch delegation to A2A `message/send`; remove direct use of `/agent-chat/{target}` from the delegate command path.
- Generate server-side `Task.id` and `Task.contextId`.
- Store `runtime_session` separately from `contextId`.
- Store `submitted`, run target chat in a control-plane-owned background worker/goroutine, update final status.
- Mark stale `submitted`/`working` tasks as `unknown` on control-plane startup.
- Add bearer auth and task visibility enforcement.
- Add `GET /tasks/{id}` convenience endpoint.
- Add `clutch delegate --async` and `clutch tasks get`.

Phase 2:

- Add target session proxy.
- Add `clutch session <agent> <name>`.
- Include session URLs in `Task.metadata.clawmatrix`.
- Add final text and session-link artifacts.
- Add `tasks/cancel` as best-effort.

Phase 3:

- Add `message/stream`.
- Add `tasks/resubscribe`.
- Emit `TaskStatusUpdateEvent` and `TaskArtifactUpdateEvent`.
- Add state transition history.

Phase 4:

- Add richer skill/capability metadata from agent-published info.
- Add push notification config if needed.

## No Legacy Delegation Contract

`clutch delegate` is a friendly CLI wrapper over A2A `message/send`.

The old `/agent-chat/{target}` and clutch `/delegate/{target}` protocol do not need to remain stable. They can be removed, kept temporarily as internal adapters during migration, or rewritten to call the A2A handler. The product contract should be A2A.
